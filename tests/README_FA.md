# آزمون‌های SALLY

این آزمون‌ها نوشته شده‌اند و در محیط Work فعلی اجرا نشده‌اند؛ .NET SDK در دسترس نیست. هیچ نتیجه موفقی برای C#، Razor یا SQL از وجود این فایل‌ها استنباط نشود.

`Shop.Security.Tests` از TestServer و دیتابیس حافظه‌ای مستقل استفاده می‌کند. در Host آزمون، ShopDbContext با Context آزمایشی جایگزین شده، SMTP خالی و Hangfire خاموش است؛ اتصال به دیتابیس ShopDb لازم نیست.

روی محیط توسعه .NET 8، از ریشه Shop:

```powershell
dotnet test tests/Shop.Security.Tests/Shop.Security.Tests.csproj
```

این فرمان آزمون و Compile آزمایشی است؛ Build نهایی یا Publish نیست. شامل انقضا و وابستگی توکن بازیابی به حساب/رمز/ایمیل، رد توکن خراب، منع مدیریت برای مهمان، منع ارتقای Cookie مشتری حتی با نقش Administrator، و رد نشست قدیمی پس از تغییر رمز است.

در بسته یکپارچه ۲۰۲۶/۱۰/۳۰، پروژه آزمون و ابزار هش مدیر داخل Shop.sln نیز هستند؛ Build Solution در حالت Debug هر شش پروژه را کامپایل می‌کند. راهنمای جایگزینی سورس، بیلد، ساخت کپی مستقل تست و پروفایل SALLY_TEST در `../SALLY_TEST_PACKAGE_FA.md` است. Fixture سایز با Apply=0 پیش‌نمایش است و ShopDb را به‌عنوان مقصد نمی‌پذیرد. این آماده‌سازی به معنی اجرای آزمون نیست.

آزمون‌های SQL باید جداگانه و فقط روی دیتابیس آزمایشی مستقل اجرا شوند. از InMemory نمی‌توان صحت Lock، Rollback، FK، Compare-and-swap یا SQL Server را نتیجه گرفت. موارد لازم:

1. دو سبد هم‌زمان برای آخرین موجودی یک سایز: تنها یکی باید موفق شود؛ هیچ موجودی منفی نشود.
2. دو Submit هم‌زمان برای یک سبد: یک Order و یک بار کسر موجودی؛ پاسخ تکراری همان Order.
3. تغییر تعداد سبد هم‌زمان با Checkout: اقلام از دست نروند و سبد مصرف‌شده دوباره سفارش نسازد.
4. شکست موجودی سایز پس از تغییر جمع محصول: همه تغییرات Rollback شوند.
5. دو لغو هم‌زمان: موجودی فقط یک بار برگردد؛ تاریخچه Order/OrderItems حفظ شود.
6. ویرایش قدیمی فرم موجودی پس از Checkout: تغییر جدید را بازنویسی نکند و خطای Reload بدهد.
7. تغییر قیمت هم‌زمان با Checkout: قیمت و جمع اقلام سفارش با مبلغ ذخیره‌شده برابر باشند.
8. استفاده هم‌زمان دوباره از لینک بازیابی: فقط یک تغییر رمز موفق شود؛ Cookie قدیمی رد شود.
9. تغییر هم‌زمان ایمیل/رمز و لینک تأیید: مقصد قدیمی و لینک منسوخ معتبر نمانند.
10. قطع SMTP قبل و بعد از پذیرش پیام، و قطع SQL پس از پذیرش SMTP: وضعیت واقعی تحویل و احتمال تکرار بررسی شود.
11. سفارش عضو و مهمان، ایمیل ثبت و لغو، ایمیل تأیید و بازیابی روی Sandbox ارسال بررسی شوند.

قبل از هر پیشنهاد Schema، `scripts/audit-current-database-READ-ONLY.sql` روی دیتابیس موجود بررسی شود. اجرای Migration یا Seed روی دیتابیس موجود نیازمند تأیید کاربر است. هیچ عملیات پاک‌سازی دیتابیس یا Docker در این آزمون‌ها وجود ندارد.
